Eternity II looks like a natural GPU problem. Fix the first rows of the board
and you get millions of independent subtrees; nothing one subtree learns
matters to another. The community saw this in June 2007, weeks before the
puzzle shipped, and argued about it for the next nineteen years.

This page separates three things that earlier versions of it blurred
together: the 2011 argument that GPUs would not help, the measurements people
have actually made since, and the questions nobody has answered yet. Short
version: the 2011 argument described the hardware of its time, the
measurements consistently show large constant-factor wins, and no tuned
full-board GPU solver has been published. None of this changes the
[larger point](/research/why/prune-vs-speed) that a constant factor, on a CPU
or a GPU, does not make exhaustive search of the full puzzle feasible.

## The early proposals

In June 2007, Simon Chapple floated brute-force solving on Nvidia's 8800
cards, and a member posting as James guessed a GPU might make a solver "maybe
4 or 5 times" faster
([message 351](https://groups.io/g/eternity2/message/351),
[message 355](https://groups.io/g/eternity2/message/355)). In May 2008 came
the CUDA question, answered by a member who was "nearly done" with a
GLSL-based CSP solver that was never heard from again
([message 5407](https://groups.io/g/eternity2/message/5407),
[message 5409](https://groups.io/g/eternity2/message/5409)). In 2010 Thomas
asked the first OpenCL question: he owned hardware capable of more than 10¹²
operations per second "but unfortunately I miss a suitable program which can
use it" ([message 7653](https://groups.io/g/eternity2/message/7653)). The
missing program, not the hardware, would remain the limiting factor.

## The 2011 argument, and what it assumed

In November 2011 Mike Field posted the archive's best-known argument against
GPUs ([message 9003](https://groups.io/g/eternity2/message/9003), typo fix in
[message 9004](https://groups.io/g/eternity2/message/9004)). He started from a
measurement: his backtracker placed 75 million tiles per second per core on a
2 GHz AMD, about 26 cycles per tile, while the instruction count came to
roughly half that. About half the time the core was waiting on memory: a
chain of small dependent loads (candidate table, piece data, board state,
branch).

He then laid out a fork. GPU workers either cooperate, which needs
synchronization bandwidth the hardware did not provide, or work alone, in
which case each needs its own tables and search state, which he estimated as
too large for the roughly 8 KB of fast local memory per stream processor.
Either way the state spills to external memory and every worker queues on the
same bus. He concluded that neither GPUs nor FPGAs could gain an order of
magnitude over a CPU core.

Three assumptions in that argument have not held up.

- **Latency is not bandwidth.** Waiting on a chain of dependent loads is a
  *latency* problem. GPUs are designed for it: each streaming multiprocessor
  keeps many independent threads in flight and switches to another whenever
  one stalls. Eternity II supplies effectively unlimited independent
  subtrees, which is the condition latency hiding needs. Field's remark that
  "a 128 bit memory bus will be little quicker than a 16 bit one" is about
  DRAM transactions, and stops mattering once the working set lives on chip.
- **The state is small, and most of it is shared.** The lookup tables are
  read-only, so all threads on a multiprocessor can share one copy in shared
  memory or cache. Field's own 2014 FPGA design fit those tables in about
  4 KB and each solver's private state in about 1 KB
  ([FPGA page](/research/build/hardware/fpga-solving),
  [message 9226](https://groups.io/g/eternity2/message/9226)), and Miles's
  GPU solver packed a partial board into 20 bytes
  ([message 9814](https://groups.io/g/eternity2/message/9814)).
- **On-chip memory has grown by orders of magnitude.** Even in 2011 the
  per-multiprocessor figures were larger than 8 KB: Nvidia's Fermi (2010) had
  64 KB of configurable shared memory and L1 plus 128 KB of registers per
  multiprocessor, and AMD's Evergreen had 32 KB of local data share and
  256 KB of registers per SIMD unit. An RTX 4090 has 128 multiprocessors,
  each with 256 KB of registers and up to 128 KB of L1 and shared memory, and
  72 MB of L2 cache behind them. At about 1 KB of private state per search,
  tens of thousands of concurrent searches fit on chip.

Field's analysis is worth reading as a record of 2011 hardware and of a
careful engineer's reasoning. It should not be read as a standing law, and
the measurements below do not support it.

## Divergence and load balance

GPU threads run in lockstep groups (warps), and a warp runs as slowly as its
slowest thread. Backtracking diverges quickly: two searches from neighbouring
prefixes are at different depths within a few placements. Adam Miles, who
built the fastest GPU solver in the archive, described the practical problem
as "keeping every processor doing something useful on every clock cycle"
([message 9984](https://groups.io/g/eternity2/message/9984)). David Barr
reported the same effect at coarser grain in 2025: subtrees differ in size,
so a run ends with "a dwindling number of active workers"
([message 11598](https://groups.io/g/eternity2/message/11598)).

Both problems are real, and both have standard treatments in the GPU
literature on backtracking and branch-and-bound
([Jenkins et al. 2011](https://doi.org/10.1007/978-3-642-23397-5_42),
[Gmys et al. 2016](https://doi.org/10.1016/j.parco.2016.01.008),
[Carneiro Pessoa et al. 2018](https://doi.org/10.1002/cpe.4374)):

- write the search as an explicit loop in which every thread executes the
  same step (try next candidate, place, or backtrack), so threads at
  different depths still run the same instructions;
- let a whole warp cooperate on one node, with the 32 lanes testing
  candidates in parallel against a used-piece bitmask;
- keep workers busy with dynamic work splitting or work stealing, so long
  subtrees are cut up and handed to idle threads
  ([Cederman and Tsigas 2012](https://doi.org/10.1016/b978-0-12-385963-1.00035-6)).

Barr's "dwindling workers" is a load-balancing problem of exactly the kind
work stealing addresses; it is not a property of GPUs. None of the published
Eternity II GPU solvers report using these techniques, so their measured
speeds are a floor, not a ceiling.

## What has been measured

**David Barr, OpenCL (2015).** The first working, published GPU solver:
PyOpenCL on a Radeon HD 7870. It fully searched one row of Martin's 10×10
first-row list in 3 h 46 m
([message 9360](https://groups.io/g/eternity2/message/9360),
[message 9364](https://groups.io/g/eternity2/message/9364)); his CPU
baseline was 120M placements/s across all 8 cores of an FX-8120
([message 9366](https://groups.io/g/eternity2/message/9366)). The source is
at [github.com/david3x3x3/eternity2](https://github.com/david3x3x3/eternity2)
([message 9367](https://groups.io/g/eternity2/message/9367)).

**Adam Miles, DirectX 12 (2018).** Miles wrote compute shaders for an Xbox
One X. A breadth-first pre-solve on the GPU enumerates every partial solution
for the first 14 to 18 tiles (3.3 million prefixes for the 7×7, 155.8 million
for the 9×9), each packed into 20 bytes, and a parallel sweep then finishes
each prefix ([message 9814](https://groups.io/g/eternity2/message/9814),
[message 9819](https://groups.io/g/eternity2/message/9819)). Brendan's 7×7
set 1 fell to 14 seconds against a 529-second optimised CPU baseline, about
38×; Barr's OpenCL solver on a GTX 1060 did it in 73 seconds
([message 9818](https://groups.io/g/eternity2/message/9818)). The same
solver then walked the entire 9×9 set 1 tree in 25 h 24 m and found exactly
the 2 known solutions, an independent confirmation of the 2011 CPU census
([message 9822](https://groups.io/g/eternity2/message/9822)).

**Joshua Blackwood (2020).** During the campaign that produced the 468 to 470
boards he measured a GPU port alongside SAT solvers and cached 2×2 blocks,
and kept none of them; refined heuristics were what paid
([message 10056](https://groups.io/g/eternity2/message/10056)). That is one
practitioner's engineering decision for his particular heuristic search, and
the archive does not record the numbers behind it.

**David Barr, RTX 4090 (2025).** His Python/OpenCL depth-first searcher on a
rented RTX 4090 (about $0.30 per hour) searched about 3.17 billion placements
per second on Brendan's 10×10. He noted that the current code "doesn't work
well with the full Eternity puzzle due to memory limitations"
([message 11598](https://groups.io/g/eternity2/message/11598)). That is a
statement about that implementation; as the state budget above shows, the
full board does not inherently exceed GPU on-chip memory.

**2026.** Asked what current engines do, Miles gave a rule of thumb of about
50 million placements per second per tuned CPU core and "north of 10
billion" for GPU solvers
([message 11826](https://groups.io/g/eternity2/message/11826)). In the same
thread Barr measured his own single CPU core at about 23 million per second
and his GPU port at about 2.4 billion, roughly 100×
([message 11835](https://groups.io/g/eternity2/message/11835)). GPUs also
appeared on the optimisation side: benj39100 ran GPU simulated annealing
with 4096 parallel replicas on the strict five-clue board
([message 11902](https://groups.io/g/eternity2/message/11902), discussed on
the [rigidity page](/research/why/rigidity-wall)). Running many independent
replicas is the kind of workload GPUs have handled well for years in
spin-model simulation
([Weigel 2012](https://doi.org/10.1016/j.jcp.2011.12.008)).

## Comparing GPU and CPU numbers fairly

Most GPU-versus-CPU figures in the archive compare a whole GPU with one CPU
core. That flatters the GPU. A fair comparison uses the same puzzle, the same
counting convention, and the same unit of hardware:

- **Same puzzle and convention.** Placement rates depend on board size and
  difficulty: McGavin's C engine runs about 287M placements per second on an
  easy board and about 105M on a hard one
  ([solver engineering](/research/build/faster/solver-engineering)), and
  engines differ in what they count. Barr's 3.17B is a 10×10 figure from one
  engine; the CPU figures come from other engines on other boards.
- **Per socket, per watt, per dollar.** A 16-core desktop CPU running a
  generated-C engine at 105M to 290M per core lands between roughly 1.7 and
  4.6 billion placements per second, the same range as Barr's 4090 figure.
  Against the 2026 claims of 10 billion and more, a GPU would be ahead by a
  few times per socket. Watts and dollars have not been measured on the same
  workload.

So the measured picture is: GPUs give large constant factors over a single
core, and plausibly a few times over a full CPU socket, with the upper end
still unpublished. Since every GPU solver in the archive is a hobby
implementation without the load-balancing techniques above, the ceiling is
not known.

## What a GPU can and cannot change

The search space does not care which chip walks it. A constant factor of 10
or 100 is useful for anything bounded: re-verifying a census, enumerating
rows or blocks, exhausting a sub-puzzle, running more annealing replicas, or
covering more restarts in a record hunt (where more attempts per hour does
raise the chance of a better board). It does not make exhaustive search of
the full 16×16 feasible, for the same reason more CPU cores do not;
[why a faster computer doesn't help](/research/why/prune-vs-speed) does that
arithmetic.

The old distinction between GPU "search" and GPU "verification" does not hold
either. Miles's 9×9 run is exhaustive depth-first backtracking, the same
algorithm a solution search runs, with a different stopping rule. What made
it work was that the 9×9 tree is small enough to enumerate, not that
verification is a different kind of workload.

## Open questions

- **A tuned full-board GPU backtracker.** Nobody has published one that uses
  work stealing, shared read-only tables and warp-level candidate testing,
  with node counts that match a reference CPU engine on the same boards. The
  budget above suggests it fits on current GPUs.
- **Per-socket, per-watt and per-dollar numbers** on the same puzzle and the
  same counting convention, against a full CPU socket.
- **GPU population methods for the record hunt.** Annealing, parallel
  tempering and similar methods with thousands of replicas have only just
  appeared on this problem.

If you take a run at any of these, [contributing](/research/contribute) the
code and numbers gives them a permanent home here.
